# src/cli/

The command-line front end (`dq8ctl`). Exposes the same operations as the launcher (verify, setup, build, run, diagnose) for scripting, CI and headless use. Links `dq8::core` only (architecture.md §13.2) and has no dependencies beyond it; argument parsing is hand-rolled. `cli.h` holds what the command files share (exit statuses, the JSON writer, argument parsing, data-directory lookup); `main.cpp` has `verify`, `extract` and `info`, `recomp_commands.cpp` has `recomp` and `make-unit-elf`, `setup_commands.cpp` has `setup`, `run` and `diagnose`, `settings_commands.cpp` has `settings`.

Commands (M1, M2):

| Command | What it does |
|---|---|
| `verify <iso> [--regions DIR] [--json]` | Identify the disc from its boot file and cross-check it against the region profiles: ELF headers and segments, listed files, and every overlay's `MWo3` container header against its profile row and ELF segment (one `overlay:` line each; `overlays` in JSON). |
| `extract <iso> [--out DIR] [--regions DIR] [--force] [--emit-profile] [--no-verify-hashes] [--json]` | Copy the boot file, overlays and IOP modules into `DIR/<profile id>/` (default `baserom/`). Re-runs skip files that are already present and intact. `--emit-profile` prints the profile rows with the observed sizes and hashes on stdout (status lines go to stderr) so a developer can paste them into `data/regions/`. |
| `info <iso>` / `info <boot elf>` / `info <overlay .BIN> [--regions DIR]` | Volume facts, SYSTEM.CNF, the listing with LBA and size, the path-table cross-check; or the ELF header and its segments; or an `MWo3` container's header fields, derived addresses (text, data, bss, constructor table), the 16 raw header words, and whether the region profile that owns its window records the same values (reported, not enforced: `info` describes, `verify` judges). The kind is detected from the file's magic. |

| `recomp prepare\|generate\|build\|all <iso> [--work DIR] [--maps DIR] [--units LIST] [--jobs N] [--ps2-recomp PATH] [--module-template DIR] [--abi-include-dir DIR] [--cmake PATH] [--generator NAME] [--force] [--no-pch] [--debug-info] [--verbose] [--json]` | Stages 3 to 6 of the setup pipeline over a work directory (default `work/recomp`; architecture.md §3): `prepare` verifies the disc and writes each unit's ELF and recompiler config from the function maps (default `<work>/maps`), `generate` also runs `ps2_recomp` per unit, `build` (and its alias `all`) also builds each unit through `cmake/module` into `<work>/modules/<profile>/` with `build-manifest.toml`. Each stage brings the earlier ones up to date and skips unchanged work, so a re-run is a no-op and an interrupted run resumes. Units: `main`, then the overlays in name-table order (`title`, `casino`, `viewer`, `battle`, `menu`, `shop`). Ctrl-C stops the running tool tree. The recompiler defaults to the one this build made, then `ps2_recomp` beside `dq8ctl`, then `PATH`; the template and ABI headers are found in the source tree or the install. |
| `recomp <stage> --unit-elf NAME=PATH... [--profile-id ID] [...]` | Developer mode (synthetic tests, experiments): the same stages over given unit ELFs instead of a disc; `main` is the main unit, any other name an overlay (its id read from the container at the start of its code). |
| `make-unit-elf <overlay .BIN> --out FILE [--boot ELF] [--regions DIR] [--json]` | Write one overlay's unit ELF (`make_overlay_unit_elf()`), checked against the window of the profile that owns its load address; `e_flags` from `--boot`, else 0. |

Commands (M5, `Docs/milestones/M5-launcher.md`):

| Command | What it does |
|---|---|
| `setup <iso> [--events FILE\|-] [--jobs N] [--force] [--maps DIR] [--work DIR] [--registry FILE] [--no-smoke] [--smoke-input FILE] [--allow-download] [--ps2-recomp PATH] [--game PATH] [--regions DIR] [--json]` | The first-run setup through `setup::run()`, the same code the launcher runs: verify (and the free space), extract, toolchain, maps, prepare, generate, build, smoke test, register. The work directory defaults to `build/` in the user data directory, the maps to the published ones (`--maps DIR`: contributor maps). `--events -` prints the stage events as JSON lines on stdout (`--events FILE` into a file); otherwise readable lines. Ctrl-C cancels (`setup-cancelled`); a later run resumes, and stages that are up to date report `skipped`. `--allow-download` is the consent to fetch the bundled toolchain (Windows, ADR-0018); without it a missing bundle is `toolchain-incomplete`. The recompiler and `dq8-game` default to the ones this build made, then the ones beside `dq8ctl`. |
| `settings list\|get KEY\|set KEY=VALUE...\|reset [KEY...]\|defaults [--config FILE] [--profile ID] [--json]` | The user settings file (default: `settings.toml` in the user configuration directory, or beside the program with a `portable` marker). `set` also takes `KEY VALUE`; `--profile ID` reads and writes the `[profile.ID]` tables; `reset` without keys clears the layer; `defaults` writes every setting at its default. Unknown keys and comments are kept. |
| `run [--profile ID] [--config FILE] [--registry FILE] [--game PATH] [-- dq8-game options]` | Starts `dq8-game --iso ... --module-dir ... --config <user file> --window` for a registered build (the first, or `--profile`); options after `--` are passed on (`--headless` replaces `--window`). Its output streams through; the exit status is the game's. |
| `diagnose [--out FILE] [--config FILE] [--registry FILE] [--work DIR]` | The diagnostics report (`dq8/core/diagnostics.h`) on stdout or into a file: system, toolchain, settings, builds and their manifests, the setup log's event lines. Never game data. |

Exit status: 0 success, 1 the image does not match a profile or an extracted file's hash differs, 2 usage, I/O or tool error (`recomp` failures carry codes such as `map-invalid`, `recomp-failed`, `module-build-failed`, `tool-missing`). `--regions` defaults to `data/regions` under the current directory, under an ancestor of the executable (the build tree) or `share/dq8/regions` beside it.

`--json` prints one object on stdout: `{"ok": true, ...}` or `{"ok": false, "error": {"code": "<ErrorCode name>", "message": "..."}}`. That object, and the `ErrorCode` names in it, are the contract the launcher will consume; add fields freely, never rename or remove them.
